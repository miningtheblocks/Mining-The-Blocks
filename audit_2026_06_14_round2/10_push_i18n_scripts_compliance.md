## Top 5 críticos

1. **[CRIT-10-01] `notifyAllUsers` envía broadcast a Expo Push API mientras los clientes registran tokens FCM nativos → todo el broadcast falla silenciosamente** — `functions/index.js:1647-1655` vs `App.js:212` + `functions/index.js:1068-1073`. El cliente en `App.js:212` llama `Notifications.getDevicePushTokenAsync()` y guarda `pushTokenType: 'fcm'` (App.js:224). `sendPushToUser` (línea 1068) ramifica correctamente por `tokenType === 'fcm'` y usa `getMessaging().send({ token, … })`. Pero `notifyAllUsers` (línea 1647) NO ramifica: arma chunks de 100 y los manda **siempre** a `https://exp.host/--/api/v2/push/send`. Expo Push API recibe el token FCM como `"to"` y responde `{"status":"error","message":"\"ExponentPushToken[xxx]\" is not a registered push token"}` — el fetch no tira excepción, suma `sent += chunk.length` igual, y el audit log dice "sent=N" cuando en realidad **fueron 0**. Resultado: la única broadcast feature funcional del producto (alertas a toda la base de jugadores cuando hay nueva capa, evento, mantenimiento, alerta de seguridad) NO entrega ningún mensaje, y el admin no se entera porque el log dice success. Fix: replicar el branch `fcm`/`expo` en `notifyAllUsers` cargando `pushTokenType` por usuario; o mejor, usar `getMessaging().sendEachForMulticast(...)` que acepta hasta 500 tokens FCM por request y devuelve `successCount`/`failureCount`. Cruza con [HIGH-10-02] (limpieza de tokens inválidos).

2. **[CRIT-10-02] Toggles de notificación en `Config.js` son 100% cosméticos — el backend NUNCA los lee** — `Config.js:14-17 + 85-93` ↔ `functions/index.js:1056-1084 + 1191-1196 + 1543 + 1563-1567`. Confirma y AMPLÍA [CRIT-FE-01] del Agente #4. El cliente persiste `notifyAdReady`, `notifyDaily`, `notifyRewards`, `notifyNewLayer` en `users/{uid}.settings.*` (línea 68 de Config.js: `setDoc(ref, { settings: settingsRef.current }, { merge: true })`). Pero `sendPushToUser` solo lee `data.pushToken` y `data.settings.language` — **JAMÁS** consulta `settings.notify*`. Verificación textual:
   ```
   grep -n "notifyAdReady\|notifyDaily\|notifyRewards\|notifyNewLayer" functions/index.js
   (sin resultados)
   ```
   Por lo tanto, todas las invocaciones de push (mint NFT, referral bonus, payment received) ignoran las preferencias del usuario. **Implicancia compliance**: una autoridad regulatoria (UE/GDPR) o Google Play (cuando intenten subir) puede considerarlo "dark pattern" — UI muestra control que no existe. Si el usuario apaga "Recompensas agregadas" y sigue recibiendo pushes, puede reportar la app. Fix: en `sendPushToUser` pasar un `notifyKey` (e.g. `'rewardsAdded'`) y skip si `data.settings.notify<Key> === false`.

3. **[CRIT-10-03] `sendPushToUser` y `notifyAllUsers` NO limpian tokens inválidos** — `functions/index.js:1056-1084 + 1655-1660`. Cuando FCM responde `messaging/registration-token-not-registered`, `messaging/invalid-registration-token`, o `messaging/mismatched-credential`, ambas funciones logean y siguen. Los tokens quedan en Firestore para siempre. Consecuencias:
   - **Costo Firestore**: cada `notifyAllUsers` paga reads por usuarios con tokens muertos (probablemente 30-50% de la base tras 6 meses de churn).
   - **Costo FCM**: la cuota gratuita de FCM no aplica por mensaje fallido, pero los `getMessaging().send()` igual cuentan reads del SDK admin y rate-limits del proyecto.
   - **Cross-user leakage**: si el device A se reseteó y el token migró al device B (mismo APK, otro usuario), el push del usuario antiguo (referral bonus, mint NFT) llega al usuario nuevo con datos del anterior. Combinado con que **`logout NO limpia pushToken`** (Agente #6 MED-23), es vector de privacy leak.
   - **Bombing**: si el atacante manipula DB de un usuario test (vía firestore rules bug) puede setear `pushToken` con valores aleatorios y FCM bloquea el proyecto entero por abuse.
   Fix: en el catch de `sendPushToUser`, si `e.code` matchea `messaging/registration-token-not-registered` u `messaging/invalid-registration-token`, hacer `await db.collection("users").doc(uid).update({ pushToken: FieldValue.delete(), pushTokenType: FieldValue.delete() })`. En `notifyAllUsers`, `sendEachForMulticast` devuelve un array `responses[]` con `error.code` por token — barrer y limpiar.

4. **[CRIT-10-04] `i18n.t()` SIN motor de interpolación + escape — cada call site reimplementa `.replace('{n}', value)`** — `i18n.js:1037-1052`. La función `t(key)` solo lookup + fallback a EN; NUNCA acepta un segundo parámetro de variables. En 17 call sites distintos el frontend hace `t('foo').replace('{n}', value).replace('{m}', other)`. Problemas en serie:
   1. **Sin escape**: si `value` contiene `{n}` o `{m}` (por ejemplo `displayName` con `"hola {url}"` que sigue siendo válido en usernames), el siguiente `.replace` lo interpreta. Es XSS-equivalente en el sistema de templates: un atacante con `displayName = "{code}"` rompe el flow de invitación.
   2. **Sin escape de HTML entities**: no aplica en RN (`<Text>` no parsea), pero sí en `verify.html` (Agente #7) si alguna vez se comparte código.
   3. **Type coercion silencioso**: `replace('{n}', undefined)` → "undefined" literal en pantalla. En `ChainHistoryScreen.js:88` `item.episodeNumber ?? '—'` mitiga, pero en `Profile.js:42` `referralShareMsg.replace('{code}', code).replace('{url}', url)` si `code` es null se imprime `null`.
   4. **Claves faltantes silenciosas**: `t('profile.walletCooldown')` (Profile.js:97) y `t('profile.emailNotVerified')` (Profile.js otro lugar) NO existen en `i18n.js`. `t()` devuelve el key como string ("profile.walletCooldown") y luego `.replace('{h}', h)` no matchea → user ve el key literal. Confirmado con grep.
   5. **Strings hardcoded fuera del sistema**: `GetPeaks.js:203` `<Text>picks</Text>` está hardcoded (en EN) — usuarios en español ven "picks" en lugar de "picos". `BuyCredits.js:170` `<Text>$15 <Text>USDC</Text>` igual.
   Fix: rehacer `t()` para aceptar `t(key, vars)` con un loop sobre `Object.entries(vars)` que use `String(v)`, y reemplace **todas** las occurrences (`replaceAll`). Agregar warning en `__DEV__` si el resultado contiene `{` sin reemplazar. Agregar suite de tests con todas las keys × interpolación.

5. **[CRIT-10-05] `scripts/grant_admin.js`, `delete_users.js`, `full_reset_game.js` cargan `firebase-tools.json` con `access_token` desde un path hardcoded del dev específico** — `grant_admin.js:25`, `delete_users.js:8`, `full_reset_game.js:19`. Confirma [HIGH-Agente-6-grant_admin] y AMPLÍA:
   - El path `'/home/code/.config/configstore/firebase-tools.json'` es **literal del filesystem del dev `code` en su máquina**. Cualquier otro dev que clone el repo tiene que editar el script (footgun de "lo cambio rápido y commiteo accidentalmente otro path").
   - El `access_token` cargado es el del usuario de `firebase login` — un **OAuth refresh token que da Owner del proyecto entero** (Firebase Console, billing, Cloud Functions, Firestore, Auth Admin), no solo `Auth Admin` o el rol mínimo. Si una pieza de malware (extensión maliciosa de VS Code, agente AI con permisos amplios, paquete npm comprometido) lee `~/.config/configstore/firebase-tools.json`, **toma control total del proyecto** — puede borrar Firestore, transferir el contrato, mintear NFTs infinitos, robar la wallet de pagos (porque puede leer Secret Manager via `gcloud secrets versions access` con ese token).
   - El audit log graba `operator: process.env.USER` (`grant_admin.js:87`, `delete_users.js:124`, `delete_servers.js:50`, `full_reset_game.js`) — **spoofeable trivial**: `USER=ceo node scripts/grant_admin.js <uid>` deja audit con "operator: ceo". Si el dev y el CEO comparten máquina o el agente IA corre con `USER` override (frecuente en docker), el audit es ruido.
   - Permisos OS: `firebase-tools.json` es `chmod 600` ✓, pero los scripts JS son `chmod 644` (cualquier usuario de la máquina puede leer y deducir que el token vive en ese path).
   Fix: (1) reemplazar `configstore` por un Service Account JSON dedicado (`MTB_ADMIN_SA=path/to/sa.json node scripts/grant_admin.js …`) con rol `Firebase Authentication Admin` únicamente, NO Owner. (2) Loguear `operator` con `os.userInfo().username` + `os.hostname()` para complicar spoof. (3) Si el SA es la ruta elegida, NO committearlo y dejar `.gitignore` para `*.json` con prefijo `service-account-`.

## Hallazgos secundarios importantes

### Push notifications (12 hallazgos)

- **[HIGH-10-06] Permiso de notificaciones se pide automáticamente sin contexto explicativo** — confirma `[CRIT-FE-01]` del Agente #4 con ángulo compliance: Apple HIG y Google Play recomiendan "pre-permission UI" (custom modal explicando el por qué) antes del prompt nativo. En **App.js:203-206** se llama `requestPermissionsAsync()` sin gate visual; si el usuario rechaza, el flow no se recupera (no hay second prompt, no hay deeplink a Settings). Implicancia futura para Play Store: politica de transparencia de permisos.
- **[HIGH-10-07] Notification handler con `shouldShowAlert: true` sin opt-out por modo "do not disturb"** — `App.js:43-47`. Las notificaciones interrumpen la pantalla del juego incluso si el usuario está en medio de minar — UX y compliance issue. Recomendación: respetar `shouldShowAlert` según `settings.notifyForeground`.
- **[HIGH-10-08] `notifyAllUsers` rate-limit por admin (1/hora) NO previene "admin-comprometida-mass-spam" durante esa hora** — `functions/index.js:1601-1607`. Si el admin se compromete, en 1 hora envía 1 broadcast con título arbitrario (max 100 char) y body arbitrario (max 500 char) a TODA la base — ej. "Tu wallet fue suspendida. Confirmá en hxxp://phishing.example/" + enlace. El rate-limit `nau_${adminUid}` no cubre el primer broadcast malicioso. Fix: agregar approve queue / 2FA hardware token / step-up auth para esta operación específica.
- **[HIGH-10-09] Push notifications NO tienen `data: {}` payload — el tap NO deep-linkea a la screen relevante** — `functions/index.js:1069-1073`. `getMessaging().send` solo manda `notification: {title, body}` y `android: {priority, notification: {sound}}`. Cuando el user tapea el push de "Tu NFT llegó!", el OS abre la app en su última screen (probablemente Login o el cubo) en lugar de `MyGems`. Para que `expo-notifications` deeplinkee, el payload necesita `data: { url: 'exp+miningtheblocks://gems' }` o un campo custom procesado por `addNotificationResponseReceivedListener`. Verificación: grep `addNotificationResponseReceivedListener` en `App.js` da 0 resultados — el handler de "tap on notification" NUNCA se registra. La feature de push es one-way display, sin engagement deeplink.
- **[HIGH-10-10] Channel Android `default` con `importance: HIGH` + sound — sin granularidad por tipo** — `App.js:51-56`. Todas las notifs (referral bonus, mint complete, payment received, broadcast) caen al mismo channel. En Android 8+ el usuario solo puede mute/unmute el channel entero. Crear 4 channels: `mint`, `payment`, `referral`, `marketing` permitiría mute granular y cumple expectativas Android.
- **[HIGH-10-11] `getDevicePushTokenAsync` (FCM nativo) requiere `google-services.json` válido en build — sin fallback si falta** — `App.js:212`. Si por error EAS Build pierde el `google-services.json` (Agente #9 vio que está en `android/app/`), el call tira `Error: Default FirebaseApp is not initialized` y el catch silencia. No hay alerta para el operador.
- **[MEDIUM-10-12] Backend `sendPushToUser` lee `pushToken` con `|| 'expo'` como default tipo legacy** — `functions/index.js:1061`. Usuarios "viejos" con `pushTokenType` ausente caen al branch Expo Push API, que para tokens FCM (Native) tira error silencioso. Es la misma raíz que CRIT-10-01 pero por usuario individual: cualquier user de versión <1.1.0 que actualice pierde push hasta que reabra la app y el `setupPushToken` reescriba el doc.
- **[MEDIUM-10-13] `pushToken` writable desde el cliente sin verificación de email** — confirma Agente #6 HIGH-13. Un attacker con cuenta no verificada puede poblar pushTokens spoofeados para que cuando otro user de su cadena reciba "referral bonus", el push vaya al device del atacante.
- **[MEDIUM-10-14] Sin tracking de `permission_denied` para offer re-prompt** — `App.js:200-207`. Si el user dice NO al permiso, la app no guarda esto. En el siguiente cold-start vuelve a pedir, anti-pattern conocido (Android marca permanently denied luego de 2 NO sin "don't ask again"). Fix: guardar `users/{uid}.settings.pushPermStatus = 'denied'` y mostrar un banner pasivo "Activá notificaciones en Settings" en Config.
- **[MEDIUM-10-15] Push token no incluye `appVersion` ni `installId`** — `App.js:220-226`. Útil para debugging "user reporta que no llegan pushes" y para deprecation gradual de cliente viejo (no podés mandar push de "tu wallet fue migrada" solo a v1.1.0+).
- **[MEDIUM-10-16] `DeepLinkHandler` en `App.js:373-388` solo matchea `exp+miningtheblocks://peaks` exact prefix — query string ignorado** — el handler no procesa `?sid=...&t=...` que `adpick.html:268` arma. Si en el futuro suman params, el handler los descarta sin warning. Combinar con [HIGH-09-04] del Agente #9 (intent filter scheme-only sin `autoVerify`).
- **[LOW-10-17] Audit log de `notifyAllUsers` incluye `title.slice(0,100)` + `body.slice(0,200)`** — `functions/index.js:1668-1670`. Si el broadcast contiene un código de descuento o link de pago, queda en Firestore `adminActions` por siempre. No es secreto pero es ruido. OK.

### i18n (10 hallazgos)

- **[HIGH-10-18] Claves faltantes en `i18n.js` se silencian — `profile.walletCooldown` y `profile.emailNotVerified`** — `Profile.js:97 + ~123`. Confirmado por grep: `walletCooldown` aparece en código pero NO en `resources.es/en`. El fallback de `t()` (línea 1037) devuelve el key string ("profile.walletCooldown") sin asterisco / `[MISSING]`. Usuarios reales ven el key en pantalla. Fix: en `__DEV__` tirar warning, en prod devolver el último segmento del key como mejor que nada.
- **[HIGH-10-19] Interpolación reentrante: `.replace('{code}', code).replace('{url}', url)`** — `Profile.js:42`, `GetPeaks.js:175`. Si `code` legítimamente contiene `{url}` (un user que llama su referralCode `{url}`), el segundo `.replace` lo interpreta. En la práctica los referral codes son `[a-z0-9]{8}` así que no hay riesgo real, pero el patrón es frágil — si en el futuro suman vars libres (e.g. displayName en push body), el bug aparece.
- **[HIGH-10-20] `setLanguage` setea Firestore sin debounce — tap rápido entre EN/ES dispara write por cada tap** — `i18n.js:994-997`. Sin throttle/debounce. Cost amplification trivial. Fix: usar `useDebounce(lang, 500)`.
- **[MEDIUM-10-21] Sin pluralización: `t('activity.timeMin')` → "{m}m ago" pero no soporta `{m}` plural** — `i18n.js:49 + 528`. "1m ago" / "5m ago" funciona porque la unidad es "m" no "minute(s)", pero `peaks.referralBonusSelfMsg`, `welcomePicksMsg` ("Recibiste 5 picos") están hardcoded con número específico. Cuando cambien las constantes (5 picos → 3), las strings se desincronizan. Recomendación: ICU MessageFormat (i18next, react-intl) o al menos un helper `tPlural(key, count, vars)`.
- **[MEDIUM-10-22] Sin soporte de fechas / formatos numéricos locales** — el código hace `(item.totalMined || 0).toLocaleString()` en ActivityScreen.js:76 sin pasar locale. Toma el del device. Si user tiene device en EN pero seleccionó ES en app, el separador decimal va por device, no por app. Inconsistencia menor pero visible.
- **[MEDIUM-10-23] `gems.found` = "¡Encontraste una gema rara!" hardcodea género (femenino "rara") — no traducible a idiomas con género gramatical estricto** — `i18n.js:330 + 860`. No bloqueante ahora, pero el approach actual no escala a idiomas con declinaciones.
- **[MEDIUM-10-24] No hay soporte RTL (árabe/hebreo)** — `i18n.js` no expone `isRTL` ni se llama `I18nManager.forceRTL()` en ningún lado. Cuando agreguen un idioma RTL, todo el layout horizontal (flexDirection: 'row') se ve mal. No bloqueante para EN/ES.
- **[MEDIUM-10-25] Strings hardcoded fuera de i18n**: `GetPeaks.js:203` `<Text style={styles.picksLabel}>picks</Text>` (hardcoded EN), `BuyCredits.js:170` `<Text>$15 <Text>USDC</Text>` (puede que en futuras versiones el precio sea variable), `Profile.js:42` valor de `referralShareMsg` con saltos `\n` que en algunos clientes share no se respetan. Total identificados: ~6 strings hardcoded fuera del sistema. Cobertura i18n: alta (~95%), pero los gaps son visibles.
- **[LOW-10-26] El reset de idioma persiste en Firestore **mientras** AsyncStorage queda con valor previo si Firestore falla** — `i18n.js:994-997`. La función `persistLanguage` setea AsyncStorage **primero**; si Firestore falla, el cliente quedó con el valor nuevo localmente pero el server no se enteró. En el siguiente cold start, `loadLang` desde Firestore puede sobreescribir con el valor viejo. Race condition leve.
- **[LOW-10-27] `language === 'es' ? 'es' : 'en'` heurística repetida en backend** — `functions/index.js:1063`. Defensive pero si en el futuro suman PT/FR, hay que cambiar en 5+ lugares. Centralizar.

### Scripts admin (7 hallazgos secundarios)

- **[HIGH-10-28] `scripts/reset_server.js` usa Application Default Credentials (sin token explícito) → depende de `gcloud auth application-default login` del dev** — `reset_server.js:11-17`. A diferencia de los otros 3 scripts que cargan `firebase-tools.json`, este script confía en ADC. Mejor patrón en términos de no leakear el OAuth token, pero **inconsistente con los hermanos**. Resultado: el dev tiene que mantener DOS credenciales en su máquina (Firebase CLI login + gcloud ADC). Confunde y aumenta la attack surface (más archivos sensibles en disco).
- **[HIGH-10-29] `scripts/delete_servers.js` valida formato de `serverId` pero NO chequea pertenencia a una whitelist explícita** — `delete_servers.js:20 + 67-74`. La regex `[A-Za-z0-9_-]{6,40}` es razonable pero un typo del operador (`abc124` cuando quería `abc123`) borra el server equivocado sin recurso. Recomendación: agregar `--list` mode que muestre todos los servers + activos antes de pedir confirmation, o requerir que el comando sea `<serverId>:<n>` donde `n` es la primera letra del `name` para forzar verificación cruzada.
- **[HIGH-10-30] `scripts/upload-to-ipfs.js` y `upload-metadata-to-ipfs.js` NO logean lo que subieron — solo los CIDs resultantes** — `upload-to-ipfs.js:55-62`. No hay audit log en Firestore de qué tier-N se actualizó / quién corrió el script. Si se sube por error una metadata corrupta y aparece en producción, no hay rollback ni timestamp. Crítico para NFTs (Agente #3 CRIT-5 marca Pinata como pin único). Fix: tras successful upload, append a `adminActions/{auto-id}` con `action: 'ipfs_upload'`, `tier`, `cid`, `operator`, `ts`.
- **[MEDIUM-10-31] `scripts/full_reset_game.js` ejecuta delete + reset secuencial sin transacción ni rollback** — `full_reset_game.js:232-234`. Si crashea entre `deleteAllAuthUsers` (paso 1) y `deleteAllFirestoreUsers` (paso 2), el sistema queda en estado inconsistente: usuarios Auth borrados, docs Firestore presentes pero huérfanos. Y entre paso 2 y paso 3, los servidores siguen activos con miembros nullos. No hay forma trivial de continuar/rollback. Recomendación: agregar `--continue` flag que detecte cada paso vía marker doc (`db.collection('resetState').doc('current').set({ phase: 1, startedAt: Date.now() })`).
- **[MEDIUM-10-32] `scripts/_confirm.js` bypass via `--yes-i-am-sure` exige que **NO** esté presente — pero `delete_users.js:163-167` y `full_reset_game.js:215-218` explícitamente bloquean ese flag** — confusión de patrón. `_confirm.js:8-11` acepta el flag, pero los scripts más destructivos lo rechazan. El patrón es inconsistente: para `grant_admin.js` y `delete_servers.js` el flag funciona (CI puede saltearlo), para los otros dos NO. Documentar o uniformar.
- **[MEDIUM-10-33] `scripts/_confirm.js` valida solo `input.trim() === project` — no es timing-safe** — `_confirm.js:22-26`. No es exploit (es input interactivo del operador), pero usar `crypto.timingSafeEqual` sería consistente con el resto del codebase (Agente #6 menciona timingSafeEqual en adSession).
- **[LOW-10-34] Hardcoded path `/home/code/.config/configstore/firebase-tools.json`** — repetido en `grant_admin.js:25`, `delete_users.js:8`, `full_reset_game.js:19`. Si cambia el `$HOME` del operador o se ejecuta en CI/cron/server, falla con `ENOENT`. Fix: `path.join(os.homedir(), '.config/configstore/firebase-tools.json')`. (Pero la solución correcta es no usar firebase-tools.json en absoluto — ver CRIT-10-05).

### Compliance — Privacy / Terms / GDPR / Play Store (8 hallazgos)

- **[HIGH-10-35] `public/privacy.html` y `docs/privacy.html` divergen — solo difieren en favicons** — Agente #7 ya tocó las diffs HTML. Verificado vía `diff`: solo cambian las 3 líneas de favicon. Pero **el contenido legal idéntico es positivo** para consistencia. La preocupación: `firebase.json` rewrites pueden servir `public/privacy.html` con favicons distintos a los `docs/privacy.html` (GitHub Pages). User puede confundirse si entra al mismo URL via dos canales y nota inconsistencias visuales (no de contenido).
- **[HIGH-10-36] `privacy.html` NO menciona Cloudflare** — Cloudflare Registrar gestiona el DNS de `miningtheblocks.com` (memoria del proyecto: "Migración a .com"). Cloudflare procesa metadata (IP del visitante, headers, geo) — bajo GDPR la simple presencia del DNS resolver es "processor". La policy lista Google/Firebase/Polygon/Pinata pero omite Cloudflare. Adicional: no menciona **GitHub** como sub-procesador (GitHub Pages hostea `docs/*` — GitHub recibe IPs de visitantes a privacy.html / terms.html / adpick.html). Compliance gap.
- **[HIGH-10-37] `privacy.html` declara "no recolecta intencionalmente datos de menores" sin mecanismo real para verificar edad** — `docs/privacy.html:118-119`. La app pide checkbox "Tengo 18+" en Registration. Esto es **declarativo** — no hay age gate real. Para Play Store / Apple, las apps con real-money gambling requieren verificación de edad fuerte (foto de ID, third-party age verification). Por sideload puede pasar, pero "menores usando" sigue siendo el caso esperado y la policy declara false con respecto a la realidad. Recomendación: ajustar la wording a "intentamos prevenir el uso por menores via age gate auto-declarativo; en caso de detección..." y considerar Veriff/Onfido si crecen.
- **[HIGH-10-38] No hay self-serve account deletion en la app — solo email a soporte** — confirma Agente #6 MED-15 con ángulo Play Store + GDPR. Google Play exige desde mayo 2024 que apps con login ofrezcan **self-serve account deletion in-app + via website**. Aunque MTB no esté en Play Store (sideload), si en el futuro intentan publicar (incluso para nuevo país / nuevo segmento), el rechazo es automático. GDPR Art. 17 ("right to erasure") exige cumplimiento dentro de 30 días — la policy promete "<30 días" (`docs/privacy.html:109`) pero depende de un humano leyendo `miningtheblocks@gmail.com`. Si el inbox se satura, el SLA falla. Fix: Cloud Function `deleteMyAccount` que requiere reauth + confirma con código por email + ejecuta delete in transaction (users/{uid}, subcollections, wallet unlinks, gemClaims marker).
- **[MEDIUM-10-39] `privacy.html` afirma retención de 5 años para "registros de canje" — pero `terms.html` dice "indefinidamente para auditoría"** — `docs/privacy.html:102` vs `docs/terms.html:267`. **Inconsistencia legal**. ## Conclusión

El push notification pipeline tiene **un bug de severidad CRIT silencioso**: `notifyAllUsers` (la única vía de broadcast a la base) está rota por mismatch FCM/Expo y nadie se entera porque el log dice success. Antes del primer evento de marketing / alerta de seguridad / mantenimiento programado, **el operador va a creer que mandó el push y nadie lo recibió** — costo reputacional alto si justo era una alerta de "wallet de empresa comprometida". Combinado con que los toggles de Config son cosméticos y que no hay limpieza de tokens muertos, el subsystem necesita un sprint completo de remediación.

El sistema **i18n es funcional pero amateur**: 251 keys únicas usadas en código, fallback EN sólido, persistencia OK, pero el motor `t()` no soporta interpolación nativa — cada call site reimplementa `.replace('{x}', value)` con riesgo de reentrancia, no warna ante keys faltantes (vi 2 confirmadas: `profile.walletCooldown`, `profile.emailNotVerified`), y la cobertura tiene huecos hardcoded (`"picks"` en GetPeaks). Reemplazar por `i18next` (15KB minificado) o un wrapper de 30 LOC resuelve todo + agrega pluralización + tests.

Los **scripts admin** son el principal vector de privilege escalation residual del proyecto. La sustitución de `firebase-tools.json` (Owner del proyecto) por un Service Account dedicado (`Firebase Auth Admin` only) es trivial y **muy** alto ROI de seguridad: si malware lee la SA puede manipular Auth pero NO el contrato, NO Firestore, NO Secret Manager, NO billing. El operador spoofeable con `USER=` también es trivial fix (usar `os.userInfo()` + hostname).

**Compliance** está **maduro pero incompleto**: privacy + terms cubren bien gambling/crypto/AML/COPPA/CCPA, pero las inconsistencias internas (5 años vs indefinidamente, CCPA mencionado mientras USA está banneado, CNZF Argentina inventado) son material que un regulador puede usar. La omisión de Cloudflare + GitHub como sub-procesadores y la ausencia de SCC disclosure son gaps GDPR concretos. **La accesibilidad es el problema más grande**: 0 `accessibilityLabel` en toda la app salvo 2 líneas, contraste sub-AA en 4+ estilos, touch targets sub-44pt. Bloqueante para Play Store / Apple Store / European Accessibility Act. La accesibilidad y el self-serve account deletion son los dos items que bloquean **cualquier** plan futuro de publicación oficial.
